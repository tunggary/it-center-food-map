# 상태 동기화·부스 알림

[설계 목차](README.md) · [API](api.md) · [운영 예산](operations.md)

## 전송 방식 결정

화면당 하나의 poller가 공개 `read_revision` RPC를 **2초 간격**으로 호출한다. Data API를 직접 호출하므로 Edge Functions 호출 수에 들어가지 않는다. 데이터 전송량·DB 부하는 여전히 발생한다. 무료 API 요청 횟수 무제한을 무한 처리 성능으로 해석하지 않는다.

무료 Realtime은 200연결뿐 아니라 **초당 100메시지** 제한이 있다. 100명에게 한 변경을 전파하는 것만으로 한도에 가까워지고, 연속 등록이나 여러 탭에서는 초과 가능하다. 따라서 앞서 대화에서 잠정 추천했던 Realtime을 최종안에서는 제외한다. 별도 WebSocket·SSE도 운영하지 않는다. [공식 한도](https://supabase.com/docs/guides/realtime/limits)

## 화면의 최신 상태

1. 최초 진입은 catalog와 화면 snapshot을 병렬로 조회하고 지도 SDK도 독립 로드한다. 조회 결과의 revision을 기록한다.
2. poller는 시작 시 0~200ms jitter를 한 번 적용한 뒤 2초 주기로 revision을 확인한다. 진행 중 호출은 겹치지 않고 응답 뒤 2초를 추가 대기하지 않는다. revision RPC timeout은 1.2초 기본안이다.
3. 값이 바뀌면 보이는 지도/랭킹을 **하나의 snapshot 응답**으로 교체한다. 상세·catalog·내 최애의 활성 query도 무효화한다. 변경이 연속이면 재조회는 하나만 실행하고 최신 필요 revision을 기록해 한 번 더 따라잡는다.
4. 데이터 응답의 revision이 필요한 revision 이상이면 동기화 완료다. 문자열은 BigInt로 비교한다. 오래된 응답을 나중에 도착했다는 이유로 덮어쓰지 않는다.
5. 등록자 화면은 poll을 기다리지 않고 성공 응답의 revision으로 즉시 상세/본인 등록을 갱신한다. 입력은 최신 본인 등록을 확인한 뒤 지운다.

목표 예산: poll 대기≤2초, revision 왕복≤0.5초, snapshot 왕복≤1.5초, 화면 적용≤0.5초, 합≤4.5초. 내부 목표이며 5초 요구 충족은 다른 브라우저 DOM 관측으로 확인한다. 타임아웃·정상 네트워크 기준은 [검증](verification.md)을 따른다.

Query key는 화면 종류/targetId/teamId/categoryId/page를 포함한다. 필터 전환의 이전 결과는 로딩 표시 없이 새 조건 결과처럼 보여주지 않는다. 같은 조건 갱신 실패 때만 마지막 성공 결과를 유지한다. 지도 pins와 랭킹의 revision이 다른 상태로 동시에 교체되지 않게 하나의 DTO로 관리한다.

## 연결 중단·유휴

- fetch 실패 또는 마지막 성공 동기화가 5초를 넘으면 갱신 중단 안내와 마지막 시각을 표시한다. 실제 API 성공으로만 연결 복구를 판단한다.
- 실패 시 최대 30초까지 backoff한다. `online`/focus/visibility 복귀는 즉시 조회한다. 불안정 상태에서 5초 성능 합격을 주장하지 않는다.
- 배경 탭은 poll 중단, 전경 탭은 사용자가 조작하지 않아도 2초 유지한다. 부스는 전경·절전 해제 운영이 필요하다. 백그라운드에서 5초 반영을 약속하지 않는다.
- 동일 브라우저 탭 수만큼 요청이 증가한다. 초기엔 탭 간 leader 선출을 도입하지 않고 실측/운영 안내로 관리한다. 성능 표본에 100참여자+부스1+관리1을 포함한다.
- 최초 오프라인으로 정적 앱조차 못 받으면 브라우저 오류다. 앱을 받은 뒤 API 실패는 앱 안내·재시도를 제공한다. PWA/오프라인 등록 성공은 제공하지 않는다.

## 부스 등록 알림

지도 갱신과 알림 재생은 별도 상태다. DB `registration_events`는 신규 등록 commit마다 하나이고 수정/삭제는 event를 만들지 않는다. 전역 revision 행 잠금으로 순서를 정의하므로 단순 sequence 발급 순서와 commit 순서 혼동을 피한다.

- 첫 부스 방문은 최초 snapshot의 revision을 기준 cursor로 저장하고 그 이후 신규 등록부터 소개한다. 동일 브라우저의 새로고침/재연결은 마지막 **표시 완료** cursor로 복구한다.
- 새로운 revision을 알면 그 값을 `until`로 고정하고 `read_events(after,until,100)`을 읽는다. 데이터 snapshot 갱신은 이 처리 완료를 기다리지 않는다.
- 메모리에는 다음 100건까지만 둔다. 서버 로그가 나머지 대기열이며 대기가 길다는 이유로 오래된 등록을 버리지 않는다. 4초/건, 사용자가 지나간 알림을 되감는 기능은 없다.
- `nextCursor`는 실제 스캔한 마지막 event revision이다. 삭제 tombstone도 결과에 남겨 전진할 수 있다. 페이지가 비었고 해당 watermark까지 모두 스캔했으면 `done=true`와 until을 반환한다.
- 데이터 수신 cursor와 화면 표시 완료 cursor는 분리한다. localStorage에는 표시 완료/삭제로 건너뛴 마지막 cursor만 저장한다. 메모리에 받았다는 이유로 완료 처리하지 않는다.
- 표시 직전 `read_announcement`로 현재 닉네임·팀·대상 이름을 조회한다. 삭제됐으면 `skip=true`로 통과한다. 조회 실패라면 cursor를 넘기지 않고 연결 복구를 기다린다.
- 표시 중 revision이 바뀌면 현재 소개 대상을 다시 확인해 정정 이름을 반영하고 삭제됐다면 내린다. 신규 알림을 추가하지 않는다.
- DOM 표시와 localStorage 기록은 원자적이지 않다. crash 시 마지막 1건 재생 가능성을 수용하며 누락을 피한다. 정확히 한 번의 UI 노출을 보장하지 않는다.

삭제된 등록 알림의 제외, 첫 방문 과거 알림 미재생, 4초 노출은 DEC-10의 **사용자 확정 정책**이다. 살아 있는 신규 등록을 소개하고 삭제된 공개 내용은 재생하지 않는다. DB event 원문에는 개인정보를 담지 않는다.

## 저장소 복원

백업 복원으로 서버 revision이 브라우저 cursor보다 작아질 수 있다. 이때 단순 대소 비교로 영원히 갱신을 멈추지 않도록 **현재 revision 감소를 감지하면** Query 캐시·부스 cursor를 버리고 최초 접속 정책으로 다시 시작한다. 더 큰 revision의 오래된 backup을 재적용하는 등의 환경 교체는 DB app_state의 `data_epoch` UUID로 구별한다. 복원/DB 교체 때 운영자가 DB epoch를 바꾼다. read_revision과 모든 snapshot의 dataEpoch가 달라지면 열린 탭도 캐시/cursor를 초기화한다.
